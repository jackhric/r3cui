# Haptics and audio

Code: `crates/ui/src/feedback.rs` (cues, patterns, scheduler, lab), `crates/ui/src/audio.rs`
(sounds), sounds generated by `scripts/gen-sounds.py` into `crates/ui/assets/sounds/`.

## Haptic hardware

Sources: `unfoldedcircle/remote-ui` (stock Qt UI, GPLv3) and `unfoldedcircle/core-api`.

- `src/hardware/hardwareController.cpp` builds `HapticUCR3(qgetenv("UC_HAPTIC_DEV_PATH"))` on the
  UCR3 (the touch slider is `UC_TOUCHSLIDER_DEV_PATH`).
- `src/hardware/ucr2/hapticUCR3.cpp` opens the file write-only on every play and writes one
  effect number as decimal ASCII, no newline. Mapping in the stock UI: Click = 1 (comment:
  "Strong click 100%"), Bump = 25 ("Sharp Tick 2 - 80%"), Buzz = 14, Error = 45.
- There is no strength or duration parameter anywhere in the stock UI; the only haptic setting is
  the enabled flag (`get_haptic_cfg` / `set_haptic_cfg`, `CfgHaptic = {enabled}`).
- Stock usage: Click on every press (`HapticMouseArea.qml`, keyboard keys, keypad); Bump on slider
  moves (rate limited to one per 30 ms) and the pull-down threshold; Error on rejected input
  fields and `ProfileSwitch`; Buzz only in `ProfileSwitch`.

### The chip: not identified upstream

No unfoldedcircle repository names the driver (a code search for `drv2605` finds nothing, and the
firmware, buildroot and kernel trees are not public). The effect numbers match the TI DRV2605 /
DRV2605L ROM waveform library exactly (1 = Strong Click 100 %, 25 = Sharp Tick 2 80 %, 14 =
Strong Buzz 100 %), so a DRV2605-family part is the working assumption. 45 is "Long Double Sharp
Tick 2 80 %" in that table.

Effect ids used in `Effect::id` come from the DRV2605 datasheet's waveform table as recalled, not
fetched, so treat everything except 1, 14 and 25 as unverified until tried on the device (the
Feedback lab has a "Raw effect" row that steps through 1 to 123 for exactly this):

| Family | soft / medium / strong | Datasheet name |
|---|---|---|
| Click | 3 / 2 / 1 | Strong Click 30 / 60 / 100 % |
| Sharp | 6 / 5 / 4 | Sharp Click 30 / 60 / 100 % |
| Tick | 26 / 25 / 24 | Sharp Tick 3 / 2 / 1 (60 / 80 / 100 %) |
| Bump | 9 / 8 / 7 | Soft Bump 30 / 60 / 100 % |
| DoubleClick | 30 / 28 / 27 | Short Double Click Strong 30 / 80 / 100 % |
| Buzz | 50 / 48 / 14 | Buzz 4 (40 %) / Buzz 2 (80 %) / Strong Buzz 100 % |
| Alert | 15 | 750 ms alert |
| LongBuzz | 118 | Long buzz for programmatic stopping (may need a stop write) |
| RampUp | 86 / 84 / 82 | Ramp up short / medium / long smooth 1 |
| RampDown | 74 / 72 / 70 | Ramp down short / medium / long smooth 1 |

Open questions for the device: does the file accept ids above 25 (library 6 / LRA); does writing
`0` stop a long effect; how long each effect lasts (all `after_ms` values are guesses); whether
two quick writes cut the first effect short.

## Engine

- `feedback::play(Cue)`, `play_at(Cue, Strength)`, `stop()`, `raw(id)`, `ui_event(name)`. All send a
  message to the `feedback` worker thread and return; only that thread touches the motor file and
  the audio backend. A repeating cue (`Cue::Rumble`) runs until `stop()` or its `max_ms`.
- A cue is `Cue::spec()`: steps (`effect`, `boost`, `after_ms`), default strength, priority,
  `drop_if_busy`, `min_gap_ms`, optional sound. `boost` shifts the strength per step (ramps).
- Interruption: a cue never interrupts a higher-priority one; a `drop_if_busy` cue (tick, limit
  bump) is dropped while something of equal priority is playing; otherwise the new cue replaces
  the current one. `min_gap_ms` rate-limits each cue. There is no queue, so mashing cannot build a
  backlog (`mashing_cannot_queue_a_backlog`).
- `Player` is pure and takes the time as an argument; the tests inject it.
- Settings (`config/settings.json`): `haptics_enabled`, `haptics_intensity` (0 to 1; below 0.67
  everything drops one strength, below 0.34 two; 0 is off), `sound_enabled`, `sound_volume` (0 to
  1). The core's `get_haptic_cfg.enabled`, `get_sound_cfg.enabled` and `.volume` (0 to 100) are
  read at start and must also allow it; volume is the product.

### Event table

`cue_for` in `feedback.rs` (Slint calls `root.haptic(Haptic.page)` and the like; `Haptic` is an enum in `ui/types.slint`), plus `SLIDER_MUTE` and
`SLIDER_LIMIT` for the Rust side:

| Event | Cue |
|---|---|
| any hard key on the home screen (not repeats) | tap |
| list focus moves (d-pad up/down) | tick |
| list row activated (touch or OK) | select (with sound) |
| back (key, touch, escape) | back |
| power key hold begins | rumble (repeating tick) |
| power hold completes | success (double tick, sound) |
| home key hold begins (after 160 ms) | hold ramp-up (eight clicks rising over 640 ms) |
| home hold completes | hold complete (buzz plus click) |
| power or home released early | stop |
| slider double tap (mute) | select |
| slider pushed against 0 or the limit | limit bump |

Not hooked: error (nothing in the UI reports a user-facing error yet; the Wi-Fi join failure page
is the obvious place).

## Feedback lab

Menu, then "Feedback lab" (the old About row). Rows: strength (cycles cue default, soft, medium,
strong, applied to the cue rows), constant buzz (starts and stops the rumble), raw effect (plays
the shown id, then moves to the next, 1 to 123), six cues a page, and "More cues" to turn the
page.

## Audio

Findings from `remote-ui`:

- Sounds are played by the UI process, not the core: `src/ui/soundEffects.cpp` makes five
  `QSoundEffect` objects (Qt Multimedia) on the default output device. Files are read from
  `$UC_SOUND_EFFECTS_PATH`: `click.wav`, `click_lo.wav`, `confirm.wav`, `error.wav`,
  `zap_future.wav`. With the variable unset nothing plays. There is no explicit ALSA or
  `/dev/snd` code; the Qt build uses its ALSA, PulseAudio or GStreamer backend.
- Volume and enable come from the core: `get_sound_cfg` / `set_sound_cfg`, `CfgSound = {enabled,
  volume 0..100}`; no core message plays a sound.
- `openspec/specs/hardware-platform/spec.md` says the firmware's sound files are deliberately not
  exposed to a custom UI's sandbox, so a custom UI ships its own WAVs. Whether the sandbox lets it
  open the audio device is not documented. `docs/adr/0016` in remote-ui lists "sound output" among
  the few things the UI touches directly, which suggests it can, but that is not confirmed.
- Whether the UCR3 has a loudspeaker is not documented; the voice-assistant spec streams speech
  responses to an audio player, so there is an output of some kind.

State here:

- Sounds: `confirm`, `success`, `error` (16 kHz mono 16-bit, 1.5 to 6 KB), made by
  `scripts/gen-sounds.py` and embedded with `include_bytes!`.
- Backend trait in `audio.rs`. Desktop: pipes the volume-scaled WAV to `aplay` from a detached
  thread (silently off if `aplay` is missing). Device: a silent backend; at start it logs the
  `/dev/snd` nodes and whether any playback node (`pcm*p`) can be opened for writing
  (`audio: /dev/snd` in the log), which answers the sandbox question.
- Missing: a device backend. Raw PCM through `/dev/snd/pcmC*D*p` needs the ALSA ioctls
  (`HW_PARAMS` and `SW_PARAMS`, `PREPARE`, then writes) and the card's supported formats, none of
  which can be written blind. Next step once the probe shows the node is writable: a small ioctl
  backend via `libc`, which `evdev` already pulls in.
